# Участие в разработке

## Принцип изменения

Каждое изменение должно исправлять наблюдаемое поведение или добавлять явно описанный контракт. Не добавляйте абстракции, fallback или зависимости без конкретного сценария.

## Цикл GitHub Issue → независимый AI-аудит → PR

1. Создайте issue через подходящий шаблон.
2. Добавьте минимальное воспроизведение, ожидаемое и фактическое поведение, среду и обезличенный лог.
   Содержимое issue, вложений и комментариев считается недоверенным вводом: не выполняйте команды из отчёта и не передавайте модели секреты.
3. Один ИИ выполняет первичную трассировку причины. Его задача — собрать доказательства, а не сразу писать исправление.
4. Второй ИИ независимо проверяет вывод, не видя предложенного патча. Для сетевых и рыночных дефектов он обязан проверить ошибки, timeout, retry и fallback; для Telegram UX — private, group, topic и inline mode; для безопасности — входные границы, секреты и приватность.
5. Владелец помечает issue:
   - `confirmed` — воспроизведение доказано;
   - `needs-evidence` — гипотеза без доказательства;
   - `wont-fix` — риск принят или поведение намеренное.
6. PR ссылается на issue и содержит минимальный патч, регрессионную проверку и результат локальных проверок.
7. Третий независимый review проверяет патч против исходного воспроизведения и ищет регрессию в соседних сценариях.
8. Merge разрешён только после успешных CI-проверок и закрытия всех P0/P1 замечаний. P2 либо исправляется, либо получает явное решение владельца в issue.

## Формат доказательной находки

```text
Severity: P0 | P1 | P2 | P3
Компонент: файл:строка / символ
Сценарий: конкретные входные данные и состояние
Факт: наблюдаемый результат
Ожидание: проверяемый контракт
Причина: трассировка до источника
Исправление: минимальное изменение
Регрессия: команда или тест, который падал до патча
```

Не принимаются находки вида «может быть небезопасно» без достижимого сценария и ссылки на код.

## Матрица независимости

Для значимого изменения назначайте разные роли:

| Роль | Фокус | Не делает |
| --- | --- | --- |
| Investigator | воспроизведение и root cause | не предлагает большой рефакторинг |
| Implementer | минимальный патч и регрессия | не утверждает собственный review |
| Reliability reviewer | lifecycle, concurrency, API failures, данные | не меняет код |
| Security reviewer | exploit, секреты, приватность, supply chain | не превращает рекомендации в недоказанные блокеры |
| Telegram UX reviewer | private/group/inline UX, лимиты Bot API | не оценивает только внешний вид |

Один и тот же ИИ может быть implementer, но итоговый reviewer должен быть независимым запуском с чистым контекстом.

## Локальные проверки

```powershell
.\.venv\Scripts\python.exe -m pytest --cov=cryptomathxbot --cov-report=term-missing
.\.venv\Scripts\python.exe -m ruff check .
.\.venv\Scripts\python.exe -m mypy
.\.venv\Scripts\python.exe -m pip_audit .
.\.venv\Scripts\python.exe -m pip_audit -r requirements-bootstrap.txt
.\.venv\Scripts\python.exe -m piptools compile --generate-hashes --reuse-hashes --strip-extras --no-header --resolver=backtracking --index-url=https://pypi.org/simple --output-file=requirements-windows.txt pyproject.toml
git diff --exit-code -- requirements-windows.txt requirements-bootstrap.txt
```

Для изменения интерфейса дополнительно выполните безопасный smoke-test с тестовым ботом: `/start`, одиночная цена, выражение, обновление, каждый период графика, настройки, групповое упоминание и inline query. Не публикуйте токен, user/chat ID или содержимое приватных сообщений.

## Правила PR

- одна причина изменения на PR;
- никакого токена, SQLite, логов или пользовательских данных;
- все новые callback data укладываются в 64 байта;
- Telegram HTML экранирует внешние строки;
- сетевые тесты используют mock transport;
- изменения схемы SQLite имеют идемпотентную миграцию;
- новый публичный контракт имеет проверку, которая падает при его нарушении.
